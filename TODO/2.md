Implement the following future-proof improvements. Keep the existing
Operations → Nodes → Graph → Executors architecture.

==================================================
1. Operation Parameter System
==================================================

Replace direct operation downcasting for UI parameter editing with a
generic parameter interface.

Current:

    App
      |
      v
    downcast::<Rings>()
      |
      v
    change field

Future:

    UI
      |
      v
    Operation parameter API
      |
      v
    Operation changes itself


Add a system where operations expose editable parameters.

Example:

    Rings:
        size: Number
        speed: Number
        count: Number

    Ghost:
        alpha: Number
        delay: Number

    Chroma:
        threshold: Number


Operations should expose:

- parameter names
- parameter types
- current values
- ability to update values


Do not change Value enum. Reuse the existing Value system where possible.

Keep as_any/as_any_mut temporarily if needed for internal Rust usage,
but the UI-facing API should not require knowing concrete operation types.

==================================================
2. Operation Metadata
==================================================

Add metadata to operations so external systems can inspect them.

Operations should expose:

- display name
- category
- input count
- output types
- editable parameters


Example:

    Rings
      category: Generator
      inputs: 0
      outputs: Frame


Purpose:

Enable future:

- automatic node menus
- node editors
- inspector panels
- debugging tools


Do not hardcode operation lists in JavaScript.

==================================================
3. Graph Output Management
==================================================

Add an optional output node to Graph.

Current:

    render_tick(output_node, canvas)


Future:

    Graph
       |
       output node
       |
       renderer


Add:

    Graph.output: Option<NodeId>


Benefits:

- simpler render API
- graph save/load support
- multiple preview nodes remain possible
- easier editor integration


Keep preview rendering able to render arbitrary nodes.

==================================================
4. Improve NodeId Safety
==================================================

Replace:

    type NodeId = usize


with a safer handle type.


Example:

    struct NodeId {
        index: u32,
        generation: u32,
    }


Purpose:

Prevent stale references when future features add:

- node deletion
- graph editing
- undo/redo
- loading saved graphs


Do not implement deletion yet unless required.
Prepare the type so deletion can be added later.

==================================================
5. Graph Serialization Preparation
==================================================

Prepare the graph model for saving/loading.


Do not implement full serialization yet.

Ensure:

- nodes have stable identifiers
- operations have names/types
- parameters can be represented as data
- connections are explicit


Future goal:

Save:

    Camera
      |
    Chroma
      |
    Ghost
      |
    Compose


and restore the complete effect graph.

==================================================
Implementation order:

1. Operation Parameter System
2. Operation Metadata
3. Graph Output Node
4. NodeId safety
5. Serialization preparation

Do not implement all at once. Keep each change independent.
